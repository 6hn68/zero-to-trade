# 长任务开工模板（v2，红队降级版）

> 2026-10-31 v2。红队 4 路打下来的核心教训：**默认全开是死因，条件触发是活路**。2026-11-07 并入公开仓库，原样保留。
>
> 这份文件是给贡献者的长任务开工模板，不是给新手的教程。
> 上一版第 1 行"凡是'一次干不完、要拆'的任务一律按模板开工"是错的——改掉。

## 第 0 步：先过拆分门槛（不拆是默认）

**只有同时满足才拆**，否则单 agent 一口气干完：
- 单 agent 上下文装不下，或
- 某一步出错代价极高（删库/发错货/花大钱），或
- 天然可并行的独立单元 ≥4 个

token 账：orchestrator-worker 链路是单 agent 的 4–10 倍。能一个干完就别拆。

## 第 1 步：需求五段式（写任务书用）

Context（背景）→ Goal（目标）→ Acceptance（验收标准）→ Constraints（约束：不许写文件/不许联网/预算上限等）→ Delivery（交付物清单）。
**任务书必须写"结论只放报告，不许写任何文件"**（除非本来就要产出文件）。

## 第 2 步：Architect 拆分 + 角色约束

- 拆成独立可验收单元：输入/输出/怎么算做完，一句话一个。
- 单元间依赖标顺序；无隐含依赖。
- **Contract-first**：多路要碰同一份代码/数据，先定接口契约（函数签名、JSON 格式、错误约定），再开工。
- 任务粒度 15–30 分钟/单元；模型分级：规划用强的，执行用便宜的。
- **角色约束**（三角色，不许一人分饰两角）：
- Scout：只找线索，不改代码
- Builder：最小改动，先亮 3–7 步计划再动手
- Verifier：只审不写，禁"应该没问题"式验收
- **写保护**：同一时刻只一个 Builder 有写权限；写入前 `git pull --rebase`，冲突中断本轮。

## 第 3 步：分批派发（并发卡点）

- 每批最多 3 路，派完确认 running 再派下一批。
- 协调人配比：每 10 个执行单元配 1 个协调人，向上取整。

## 第 4 步：单路独立验收 + 单路防发散

- 输出物对照验收标准打勾，不合格打回，不许"差不多"攒到最后。
- **单路纪律**：硬上限 N 轮 / T 分钟（派发时定）；红线停手——要拉大依赖、改大批文件、查不出原因→立刻停，交接只带 3 句话。
- 错了不要在对话里纠缠：直接回滚重来（`git reset` 回起点 + 改 prompt 重跑）。

## 第 5 步：心跳与部分交付

- 不许等全部回齐；完成 2–3 个单元就先交。
- 每 30 分钟无新进展：已完成 / 已失败 / 待处理三张清单。

## 第 6 步：失败处理

- 单路报错：停下，单路顺序重派最多 2 次；2 次不成记"待补"往后放。
- 协调人安静超 60 分钟无新完成：关闭，只重派剩余单元，复用已完成结果。

## 第 7 步：汇总（汇总人=最终裁决人）

- 协调人先合成单元报告；父级只做裁决和取舍，不做拼接。
- 结论冲突由汇总人裁，口径由他定，最后通写成一份。

## 上下文纪律（大任务防爆）

侦察→最小修复→全量验证三轮法：喂 Builder 只给裁剪片段 + 报错原文，不许整仓灌入；超限用 3 句话压缩交接。

## 派发指令模板（复制即用）

```
任务：[一句话]
你是[编号]，负责[你的单元]。角色：[Scout/Builder/Verifier]，只管[范围]。

[背景]
[目标]
[怎么算做完，写具体]
[约束，如：结论只放报告不许写文件；只读XX目录]
[交付物清单]

并发卡点（硬规则）：
- 每批最多派3路，派完先核对状态全部为 running 再派下一批。
- 报错不许并行重试：停下，单路顺序重派最多2次；2次不成记"待补"，先交付已完成部分。
- 不许等全部回齐才出东西：已完成的部分先交，附已完成/已失败/待处理三张清单。
- 安静超60分钟无新完成即视为卡住，由父级关闭并只重派剩余路线，复用已完成结果。

证据纪律：查不到写"未核实"，不许编。
```
